01

First: what “pstack” actually means

It is Lauren’s personal engineering stack, open-sourced as an official Cursor plugin under the MIT license. The “p” points to poteto, her handle—not “prompt,” “persona,” or “project.”

p/
Cursor plugin source

A router over an engineering system

The primary interface is /poteto-mode. It reads a principle index, picks the relevant playbook, delegates work, and requires the response to explain which principle changed which decision.

The literal expansion “poteto stack” is a strong inference from the naming pattern and community descriptions. Lauren does not appear to spell it out in one canonical sentence.

The useful takeaway

pstack is not a bag of prompts. It is a repeatable control layer that tells agents how to investigate, decide, execute, verify, and report.

03

The operating loop worth stealing

Lauren’s leverage comes from making agents capable of closing their own loops. Generation is cheap. Verification is the infrastructure.

Build the verifier first

Create a project-local, agent-friendly CLI that can drive the actual app, seed test state, handle test auth, and return structured output. Maintain a searchable Feature Map. Her rule: prove it works against the real artifact, not a proxy.

Prime context, don’t micromanage

Ask the agent to restate the underlying problem in plain English before acting. Use /how for runtime mechanics, /why for historical intent, /recall for prior conversations, and /teach to build a shared mental model.

Specify through a concrete artifact

Write the README or tutorial first, then build toward it. Lauren uses Diátaxis through /technical-writing and cleans the result with /unslop. Her stated bias: the best spec is code.

Generate options in parallel

Prototype several approaches, use /arena for bakeoffs, /architect before crossing boundaries, and /interrogate for adversarial multi-model review. Her phrase: measure a hundred times, cut once.

Fan out only after verification works

Use background poteto-agent workers, /swarm, and orchestration playbooks. She prefers Cursor cloud agents over local worktrees for high parallelism; that preference and her scale claims come from her own guide.

Own the merge

Review every diff and write your own summary. Do not pass through a subagent’s “done” report. For a second opinion, run the same prompt through a different model. Then distill the lesson back into the system with /reflect.

04

Build the GV version, not a tribute act

Your operating system already has the raw material: ATLAS, PINATA, ANVIL, deterministic-first engineering, workload-specific model routing, and a quality bar built around durability. Package those as a thin router over principles, playbooks, and verifiers.

PROPOSED REPOSITORY SHAPE
operator-stack/
├── skills/
│   ├── operator-mode/       # task router
│   ├── investigate/         # runtime + history
│   ├── verify/              # real-artifact checks
│   ├── review/              # adversarial panel
│   └── reflect/             # harvest lessons
├── principles/
│   ├── deterministic-first.md
│   ├── subtract-before-add.md
│   ├── prove-the-artifact.md
│   ├── repairable-without-builder.md
│   └── guard-context.md
├── playbooks/
│   ├── atlas-opportunity.md
│   ├── pinata-assumptions.md
│   ├── anvil-build.md
│   ├── feature.md
│   ├── bug-fix.md
│   ├── ship.md
│   └── pause-resume.md
└── verification/
    ├── feature-map.md
    ├── project-cli/
    └── evidence-schema.json
  • Start with one router.It should classify the task, load only the necessary principle and playbook files, then state its chosen path. Do not begin with two dozen slash commands.
  • Turn your existing SOPs into executable gates.ATLAS decides whether an opportunity deserves attention. PINATA attacks assumptions. ANVIL forges the product. Each stage should produce evidence the next stage can consume.
  • Make verification project-local.Every repo gets a small CLI and Feature Map tailored to its actual runtime. The shared stack defines the contract; the repo supplies the adapter.
  • Route by workload, not model loyalty.Keep model policy separate from workflows, so Cursor, Grok, Codex, OpenCode, or a future harness can inherit the same operating logic.
  • Record decisions, not transcripts.Capture the task, evidence, chosen principle, rejected options, verification result, and next safe resume point. That is portable memory without hauling the whole context window.
  • Prove it on one real repo.Pilot the stack against a feature, a bug, and a release. Only promote a rule after it changes an outcome more than once.
Best first slice

/operator-mode + five principles + three playbooks + one real verification harness. That is enough to test the architecture without recreating pstack line by line.

Models, subagents, and external tools

pstack separates the role from the model. /setup-pstack writes an always-applied model rule at ~/.cursor/rules/pstack-models.mdc; users can change budgets or use inherit-parent/auto.

What is solid—and what isn’t public

Verified from her writing

Verification-first workflow, Feature Maps, cloud-agent preference, indirect prompting, README-driven development, parallel prototypes, review ownership, and pstack’s role in her Grok Bot maintenance work.

Verified from the plugin

The 24 skills, 23 principles, 23 playbooks, two agent roles, setup rule, default model split, MIT license, and no bundled MCP config.

Not public

Her personal MCP server list, private dotfiles, private Cursor rules beyond the model-role rule, and exact day-to-day overrides.

Not yet documented

The exact pstack configuration or model mix used in the Grok Bot Galaxy build. Her public posts on Sep 15 promoted the livestream but did not publish that setup.

One useful Grok Bot bridge

/make-bot-ui builds a custom interface that wakes a Grok Bot via webhook. Lauren also publishes Dr Eggbot and tinkabot templates; those are adjacent examples, not proof of a private stack beyond pstack.
